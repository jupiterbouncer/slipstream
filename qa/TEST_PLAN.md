## 1. Objectives & Scope

This document specifies the verification plan, test cases, execution procedures, and acceptance criteria for **Slipstream Phase 2 (P2P File Transfer)**.

### Scope:
1. **Direct WebRTC DataChannel Streaming:** Validating 16 KiB chunk transmission over the `slipstream-transfer` channel without server byte routing.
2. **Chunk Boundary Verification:** Testing boundary conditions (0 B, 1 B, 16,383 B, 16,384 B, 16,385 B, 32 KiB, multi-chunk).
3. **Large-File Performance & Back-Pressure:** Verifying transfers up to the 100 MiB memory guardrail, monitoring `bufferedAmount` flow control, and rejecting >100 MiB files.
4. **Integrity & Cryptographic Verification:** End-to-end SHA-256 comparison between sender pre-hash, completion hash, and receiver reassembly digest; deliberate corruption rejection (`HASH_MISMATCH`).
5. **State Transition & Error Recovery:** User rejection, sender/receiver cancellation, connection drops, duplicate messages, and resource cleanup.
6. **Cross-Device & Mobile Responsiveness:** Verifying touch controls, QR code scanning, and responsive device-to-device trails across laptop and mobile viewports.

## 3. Test Cases Specification

### Category A: Chunk Boundary Conditions

#### TC-CHUNK-01: Zero-byte file transfer
- **Objective:** Verify handling of an empty file (0 chunks).
- **Input:** `test_0b.bin` (0 bytes).
- **Execution:**
  1. Host selects `test_0b.bin`.
  2. Host computes SHA-256 (`e3b0c44...`) and sends `file-offer` with `totalChunks: 0`, `size: 0`.
  3. Receiver accepts offer.
  4. Host sends `file-start` followed immediately by `file-complete` (0 binary chunks).
  5. Receiver verifies empty hash, acknowledges with `file-complete-ack`, and presents download.
- **Pass Criteria:** No binary chunks sent; receiver verifies empty digest; downloaded file is 0 bytes; no error.

#### TC-CHUNK-02: 1-byte minimal file
- **Objective:** Verify minimal 1-byte file transfer.
- **Input:** `test_1b.bin` (1 byte).
- **Pass Criteria:** Host sends 1 binary chunk of 1 byte; receiver validates byte length; SHA-256 matches.

#### TC-CHUNK-03: Boundary minus 1 byte (16,383 bytes)
- **Objective:** Verify single chunk of size `16 KiB - 1 B`.
- **Input:** `test_16383b.bin` (16,383 bytes).
- **Pass Criteria:** Exactly 1 chunk of 16,383 bytes; no trailing byte padding.

#### TC-CHUNK-04: Exact chunk boundary (16,384 bytes)
- **Objective:** Verify exact alignment with 16 KiB chunk boundary.
- **Input:** `test_16384b.bin` (16,384 bytes).
- **Pass Criteria:** Exactly 1 full chunk of 16,384 bytes; `totalChunks: 1`.

#### TC-CHUNK-05: Boundary plus 1 byte (16,385 bytes)
- **Objective:** Verify transition from 1 chunk to 2 chunks.
- **Input:** `test_16385b.bin` (16,385 bytes).
- **Pass Criteria:** Exactly 2 chunks transmitted in order: Chunk 0 = 16,384 B, Chunk 1 = 1 B. Receiver reassembles 16,385 bytes with zero corruption.

### Category B: Large Files & WebRTC Back-Pressure

#### TC-PERF-01: 10 MiB multi-chunk transfer
- **Objective:** Verify streaming of 640 sequential chunks with throttled progress updates.
- **Input:** `test_10mb.bin` (10,485,760 bytes).
- **Pass Criteria:**
  - Chunks 0 through 639 arrive in exact numerical order.
  - Receiver emits `file-progress` throttled to &ge; 250 ms or &ge; 1% increments.
  - Trail and percentage smoothly increment on both sender and receiver.
  - Final SHA-256 matches `aecf3c2ab...`.

#### TC-PERF-02: 100 MiB memory guardrail transfer
- **Objective:** Verify transfer of maximum allowed file size without tab crash or browser hang.
- **Input:** 100 MiB file (`104,857,600` bytes).
- **Pass Criteria:**
  - Sender back-pressure pauses transmission when `bufferedAmount > 1,048,576` bytes.
  - Sender resumes when `bufferedamountlow` event fires (&le; 256 KiB).
  - Browser memory remains stable throughout the transfer.
  - Transfer completes with valid `file-complete-ack`.

#### TC-PERF-03: File exceeding guardrail limit (> 100 MiB)
- **Objective:** Verify that files exceeding 100 MiB are rejected before streaming starts.
- **Input:** 105 MiB file (`110,100,480` bytes).
- **Pass Criteria:**
  - Sender alerts user with clear explanation before hashing/offering.
  - No `file-offer` or binary chunks sent over the data channel.
  - If forced via mock offer, receiver responds with `file-reject` (`reason: "file-too-large"`).

---

### Category C: User Rejection & Cancellation

#### TC-FLOW-01: Receiver declines offer
- **Objective:** Verify user rejection at the incoming preview stage.
- **Execution:**
  1. Sender offers file.
  2. Receiver sees filename, size, and type in incoming preview.
  3. Receiver clicks "Decline".
- **Pass Criteria:**
  - Receiver sends `file-reject` (`reason: "user-declined"`).
  - Sender stops waiting, clears transfer state, and returns to ready file selection.
  - Zero binary chunks transmitted.

#### TC-FLOW-02: Sender cancels during transmission
- **Objective:** Verify sender-initiated cancellation mid-stream.
- **Execution:**
  1. Sender begins sending 10 MB file.
  2. At approximately 40% progress, sender clicks "Cancel transfer".
- **Pass Criteria:**
  - Sender immediately stops queuing chunks and sends `file-cancel` (`cancelledBy: "sender"`).
  - Receiver discards accumulated chunks, purges partial buffer, and returns to connected screen.
  - No download link is generated on receiver.

#### TC-FLOW-03: Receiver cancels during transmission
- **Objective:** Verify receiver-initiated cancellation mid-stream.
- **Execution:**
  1. At 50% progress, receiver clicks "Cancel transfer".
- **Pass Criteria:**
  - Receiver immediately discards partial data and sends `file-cancel` (`cancelledBy: "receiver"`).
  - Sender receives cancellation, stops transmission, and returns to ready state.
  - No false success or partial download generated.

---

### Category D: Disconnection & Connection Drops

#### TC-DROP-01: Peer disconnects / closes tab during transfer
- **Objective:** Verify robust error handling when WebRTC connection drops mid-transfer.
- **Execution:**
  1. Transfer is in progress at 50%.
  2. One peer closes the browser tab or disconnects network interface.
- **Pass Criteria:**
  - `SlipstreamPeer.onChannelClose` fires.
  - Both UIs transition trail to broken state (`setTrailProgress(current, 'broken')`).
  - Heading updates to "Transfer interrupted".
  - All allocated Blob references and chunk arrays are destroyed.

#### TC-DROP-02: Signaling expiration during active transfer
- **Objective:** Verify that signaling expiration (10 min TTL in MySQL) does not affect established direct data channel.
- **Pass Criteria:** Direct WebRTC transfer continues unaffected because file bytes do not touch PHP/MySQL.

---

### Category E: Cryptographic Integrity & Hash Mismatch

#### TC-HASH-01: Deliberate hash mismatch detection
- **Objective:** Verify that corrupted file bytes fail SHA-256 verification and suppress download.
- **Execution:**
  1. Sender offers file with valid SHA-256 `A`.
  2. Simulate network corruption (or modify 1 byte in a transmitted chunk).
  3. Receiver reassembles Blob and computes SHA-256 `B` (`B != A`).
- **Pass Criteria:**
  - Receiver detects `computedHash !== offer.hash.value`.
  - Receiver emits `file-error` with `code: "HASH_MISMATCH"`.
  - Receiver discards temporary chunks; **no download URL is created**.
  - Sender receives `file-error` and marks transfer as failed.

---

### Category F: Security & Untrusted Input

#### TC-SEC-01: Malformed metadata & XSS injection in filename
- **Objective:** Verify that malicious filenames (e.g. `<script>alert(1)</script>.pdf`, `../../../etc/passwd`) are safely sanitized.
- **Pass Criteria:**
  - Filename is rendered strictly via `textContent` (never `innerHTML`).
  - Scripts do not execute.
  - Download attribute strips directory traversal characters.

#### TC-SEC-02: Unexpected binary data outside receiving state
- **Objective:** Verify that binary data received when not in `receiving` state is ignored.
- **Pass Criteria:** Ignored safely without corrupting memory or triggering file write.

## 5. Evidence & Bug Reporting Protocol

When logging test results or reporting defects, record:
1. **Transfer ID:** Shortened UUID v4 suffix (e.g. `transfer-...9f4b62`).
2. **File Size & Hash:** Exact byte count and SHA-256 digest.
3. **Environment:** OS, Browser, Device Type (Laptop / Mobile), Network Type (Local Wi-Fi).
4. **Expected Behavior:** Specific clause from `PHASE2_PROTOCOL.md`.
5. **Actual Behavior & Console Logs:** Error codes, tracebacks, or unexpected UI state.
