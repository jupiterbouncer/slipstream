# Slipstream Phase 2 — File Transfer Protocol

**Status:** Implementation contract for Phase 2  
**Protocol version:** `1`  
**Applies to:** `js/webrtc.js`, `js/file-sender.js`, `js/file-receiver.js`, `js/app.js`, `index.html`, and the transfer UI  
**Repository:** [jupiterbouncer/slipstream](https://github.com/jupiterbouncer/slipstream)

This document is the shared contract for the sender, receiver, UI, QA, and integration workstreams. Implement the same message names, fields, state transitions, and defaults. Do not independently invent or rename protocol fields. If a change is necessary, agree on it first and update this document before changing the modules.

---

## 1. Scope and architecture

Phase 2 adds **one-file-at-a-time** transfer to the working Phase 1 connection.

- The **host** is the sender. It creates the pairing session and the WebRTC data channel.
- The **joiner** is the receiver. It joins using the pairing code or QR link.
- The PHP/MySQL API remains signaling-only: session creation, SDP offer/answer, and ICE candidate exchange.
- File metadata, transfer control messages, and file bytes travel directly between browsers over the existing `RTCDataChannel`.
- The existing channel is named `slipstream-transfer` and is configured as ordered. Keep it reliable and ordered; do not set `maxRetransmits` or `maxPacketLifeTime`.
- There is one active transfer per connection. No simultaneous transfers, folder transfer, server relay, or persistent transfer history.

**Do not add Phase 2 endpoints or database columns.** The transfer protocol begins only after the data channel is open. It does not change `api.js`, the PHP routes, or the MySQL schema unless a separate, explicitly agreed signaling defect requires it.

### Existing repository baseline

The integration branch currently has:

- `js/webrtc.js`: `SlipstreamPeer`, data-channel setup, and a generic `send(data)` method.
- `js/app.js`: creates the host/joiner peer, handles the existing Phase 1 `{ type: "text", message }` test message, and has a placeholder Send-file action.
- `index.html`: loads `api.js`, `webrtc.js`, and `app.js`; it does not yet load the Phase 2 sender/receiver modules.

Preserve Phase 1 connection behaviour while adding the Phase 2 dispatch described below.

## 2. Data-channel rules

### 2.1 Two message forms on one channel

The data channel carries two distinct forms:

1. **Control message:** a UTF-8 JSON string. It describes an offer, acceptance, progress update, completion, cancellation, or error.
2. **Binary chunk:** one raw `ArrayBuffer` containing exactly one file chunk.

Do not JSON-encode file bytes, base64-encode chunks, or send file bytes through `Api`/HTTP.

Set `channel.binaryType = "arraybuffer"` when the channel is configured. The receiver should normally get `ArrayBuffer` objects for binary messages. If a browser supplies a `Blob` despite this setting, convert it to an `ArrayBuffer` before passing it to the receiver module; preserve message order while doing so.

### 2.2 Common control-message envelope

Every new Phase 2 control message must use this envelope:

~~~json
{
  "protocol": "slipstream",
  "version": 1,
  "type": "file-offer",
  "transferId": "a UUID v4"
}
~~~

Rules:

- `protocol` is always the literal string `slipstream`.
- `version` is the integer `1`.
- `type` is one of the message names in Section 4.
- `transferId` is a UUID v4 generated by the sender for each new offer. Every message and every binary chunk in that transfer belongs to this ID, even though the ID is not repeated in the raw binary payload.
- Message-specific fields are top-level fields unless the schema below explicitly places them in an object such as `file`.
- Do not add a `from` field. The local peer role and valid message direction determine which side is allowed to send each message.
- Unknown protocol versions or malformed messages must not start a transfer. Ignore stale messages for a different/finished `transferId`; report malformed or impossible messages through the error path.

Use `JSON.stringify()` to send control messages. Use the WebRTC channel's ordered delivery to preserve the sequence of control messages and binary chunks in each direction.

### 2.3 Phase 1 test-message compatibility

Phase 1 currently sends this legacy message, without the Phase 2 envelope:

~~~json
{
  "type": "text",
  "message": "Hello from the other device"
}
~~~

Keep this working while the test-chat UI remains in the application. It is **not** a Phase 2 file-transfer message and must not be passed to the sender/receiver engines. Route it to the existing chat handler. Do not reinterpret arbitrary legacy text as a file control message.

The existing `You:` / `Peer:` chat-label issue is a separate presentation/attribution bug. It does not change the file protocol. The local sender should append its own message once; the receiving peer should append the received message once, labelled as peer-originated.

## 3. Transfer metadata and chunking

### 3.1 File metadata

The `file-offer` contains the complete metadata needed for the receiver's preview and for validation. The receiver must treat every field as untrusted input.

~~~json
{
  "name": "presentation.pdf",
  "size": 524288,
  "mimeType": "application/pdf",
  "lastModified": 1794500000000,
  "chunkSize": 16384,
  "totalChunks": 32,
  "hash": {
    "algorithm": "SHA-256",
    "value": "64 lowercase hexadecimal characters"
  }
}
~~~

Field rules:

| Field | Type | Rule |
|---|---|---|
| `name` | string | Original filename for display/download; non-empty and at most 255 characters. Treat as text, never HTML. |
| `size` | integer | File size in bytes; must be a non-negative safe integer and within the receiver's configured limit. |
| `mimeType` | string | Browser MIME type; use `application/octet-stream` when the browser provides an empty value. It is advisory, not trusted. |
| `lastModified` | integer | `File.lastModified` in milliseconds since Unix epoch; use `0` if unavailable. Informational only. |
| `chunkSize` | integer | Exactly `16384` bytes for protocol version 1. |
| `totalChunks` | integer | `Math.ceil(size / chunkSize)`. A zero-byte file has `0` chunks. |
| `hash.algorithm` | string | Exactly `SHA-256` for version 1. |
| `hash.value` | string | Lowercase hexadecimal SHA-256 digest of the complete original file; exactly 64 hex characters. |

Do not send a local path, directory structure, file contents, device identity, or personal information in metadata.

### 3.2 Chunk size and ordering

- Fixed chunk size: **16 KiB (`16 * 1024 = 16384` bytes)**.
- Use `File.slice(start, end)` to produce each chunk.
- Send one chunk as one binary `ArrayBuffer` message.
- Chunks are sent in ascending order: `0, 1, 2, ... totalChunks - 1`.
- The data channel is ordered and reliable. The receiver infers the next chunk index from the number of chunks already accepted; do not add a JSON header to each binary chunk.
- For each chunk, the receiver validates its exact expected length. Every non-final chunk must be 16384 bytes. The final chunk must be `size - (chunkIndex * chunkSize)` bytes.
- No other binary payload may be interleaved with a file transfer. Since only one transfer is active and the channel is ordered, the active transfer ID and next expected chunk index identify each raw binary message.
- A binary message received when no transfer is in the `receiving` state is unexpected: do not append it to a file.

A zero-byte file is valid. It has `totalChunks: 0`; after `file-start`, the sender sends `file-complete` without sending any binary messages. The receiver verifies the SHA-256 hash of an empty file before acknowledging completion.

### 3.3 Hashing and file-size guardrail

Calculate the sender's SHA-256 digest **before** sending `file-offer`, so the receiver can compare the final result against the expected digest. Use the browser's Web Crypto API (`crypto.subtle.digest`). The standard digest API reads the complete input into memory; it is not an incremental streaming hash API.

For the initial implementation, use a configurable **100 MiB maximum file size** on both sender and receiver. This is a conservative implementation guardrail for whole-file hashing and in-memory reassembly, not a WebRTC protocol limit. Reject larger files with a clear message rather than risking a tab crash. The team may raise this limit only after testing memory use on the supported devices and updating this document.

The receiver should collect chunks in order, construct a `Blob`, read the assembled bytes for SHA-256 verification, and release references to temporary buffers after verification/cleanup. Do not offer a download before verification succeeds.

SHA-256 verifies that the received bytes match the digest announced in the offer. It does not prove who sent the file, scan for malware, or make an untrusted file safe to open. Display the filename safely and do not execute received content.

## 4. Control-message catalogue

All message examples below include the common envelope. The sender is the host; the receiver is the joiner.

### 4.1 `file-offer` — sender to receiver

Sent after the sender has validated the selected file and calculated its SHA-256 digest. It starts the receiver's incoming-file preview state, but it does **not** start byte transfer.

~~~json
{
  "protocol": "slipstream",
  "version": 1,
  "type": "file-offer",
  "transferId": "b5c7f482-9d3e-4a20-a1ef-2d1c0f9f4b62",
  "file": {
    "name": "presentation.pdf",
    "size": 524288,
    "mimeType": "application/pdf",
    "lastModified": 1794500000000,
    "chunkSize": 16384,
    "totalChunks": 32,
    "hash": {
      "algorithm": "SHA-256",
      "value": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef"
    }
  }
}
~~~

The receiver validates the envelope and metadata before showing the preview. It must not allocate the full receiving buffer or accept bytes at this point. Only one offer may be active.

### 4.2 `file-accept` — receiver to sender

Sent only after the user explicitly accepts the preview and the receiver is ready to receive.

~~~json
{
  "protocol": "slipstream",
  "version": 1,
  "type": "file-accept",
  "transferId": "b5c7f482-9d3e-4a20-a1ef-2d1c0f9f4b62"
}
~~~

The sender may begin only after receiving a matching `file-accept`. It then sends `file-start` and begins the chunks. Never send file bytes before acceptance.

### 4.3 `file-reject` — receiver to sender

Sent when the user declines or the receiver cannot accept the offer.

~~~json
{
  "protocol": "slipstream",
  "version": 1,
  "type": "file-reject",
  "transferId": "b5c7f482-9d3e-4a20-a1ef-2d1c0f9f4b62",
  "reason": "user-declined"
}
~~~

Allowed `reason` values:

- `user-declined`
- `file-too-large`
- `unsupported-file`
- `receiver-busy`
- `invalid-metadata`

The sender stops waiting, clears the active transfer, and returns to the connected/file-selection state. A rejection is not a connection failure.

### 4.4 `file-start` — sender to receiver

Sent immediately after a matching acceptance and before the first binary chunk. It tells the receiver to initialise its chunk counters and receiving state.

~~~json
{
  "protocol": "slipstream",
  "version": 1,
  "type": "file-start",
  "transferId": "b5c7f482-9d3e-4a20-a1ef-2d1c0f9f4b62"
}
~~~

The receiver must have a matching accepted offer before it accepts this message. For a zero-byte file, `file-complete` follows `file-start` with no binary chunks in between.

### 4.5 `file-progress` — receiver to sender

The receiver calculates progress from bytes it has actually received and validated. It sends progress updates to the sender so the sender's trail reflects receiver-side progress rather than merely the sender's local enqueue buffer.

~~~json
{
  "protocol": "slipstream",
  "version": 1,
  "type": "file-progress",
  "transferId": "b5c7f482-9d3e-4a20-a1ef-2d1c0f9f4b62",
  "bytesReceived": 262144,
  "totalBytes": 524288
}
~~~

Send an update at most once every **250 ms**, or sooner when progress has advanced by at least **1%**; always send the final update. Do not send one control message per chunk. The UI derives the percentage as `bytesReceived / totalBytes * 100`; for a zero-byte file, keep progress at 0 until verified completion, then show 100%.

The receiver updates its own progress immediately as each valid chunk arrives. Both UIs use the same underlying `bytesReceived` meaning.

### 4.6 `file-complete` — sender to receiver

Sent after the sender has queued every chunk, in order, onto the reliable data channel. Because the channel is ordered, this message arrives after all earlier binary chunks from the sender.

~~~json
{
  "protocol": "slipstream",
  "version": 1,
  "type": "file-complete",
  "transferId": "b5c7f482-9d3e-4a20-a1ef-2d1c0f9f4b62",
  "bytesSent": 524288,
  "chunksSent": 32,
  "sha256": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef"
}
~~~

The receiver must verify all of the following before acknowledging:

1. The active transfer ID matches.
2. The number of chunks received equals `totalChunks`.
3. The accumulated byte count and `bytesSent` both equal the offered file size.
4. `chunksSent` equals the offered `totalChunks`.
5. The computed SHA-256 digest equals both the offer hash and the completion hash.

If any check fails, send `file-error`, discard the partial data, and do not create a download URL.

### 4.7 `file-complete-ack` — receiver to sender

Sent only after all integrity checks succeed.

~~~json
{
  "protocol": "slipstream",
  "version": 1,
  "type": "file-complete-ack",
  "transferId": "b5c7f482-9d3e-4a20-a1ef-2d1c0f9f4b62",
  "status": "verified",
  "bytesReceived": 524288,
  "sha256": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef"
}
~~~

The receiver may expose the verified file for download after it has sent this acknowledgement. The sender marks the transfer complete only after receiving a matching acknowledgement with `status: "verified"`, the expected byte count, and the expected digest. Sending all chunks is not, by itself, proof of successful completion.

### 4.8 `file-cancel` — either side to the other

Sent when a user cancels an active offer/transfer. The local side must stop its work and discard its incomplete data immediately; do not wait for the acknowledgement before performing local cleanup.

~~~json
{
  "protocol": "slipstream",
  "version": 1,
  "type": "file-cancel",
  "transferId": "b5c7f482-9d3e-4a20-a1ef-2d1c0f9f4b62",
  "cancelledBy": "receiver",
  "reason": "user-cancelled"
}
~~~

`cancelledBy` is `sender` or `receiver`. Allowed reasons are `user-cancelled` and `timeout`. Do not send `file-cancel` for a connection that is already closed; perform local cleanup and show an interrupted state instead.

If the receiver initiates cancellation, it must ignore any later-arriving binary chunk for that transfer while the cancellation is being completed. If the sender initiates cancellation, it must stop queuing new chunks immediately; the ordered channel ensures already-queued sender chunks precede the cancellation control message.

### 4.9 `file-cancel-ack` — receiver of cancellation to initiator

~~~json
{
  "protocol": "slipstream",
  "version": 1,
  "type": "file-cancel-ack",
  "transferId": "b5c7f482-9d3e-4a20-a1ef-2d1c0f9f4b62",
  "cancelledBy": "receiver"
}
~~~

This confirms that the peer received the cancellation and cleaned up. It is informational; local cleanup must already have happened. Do not respond to an acknowledgement with another acknowledgement.

### 4.10 `file-error` — either side to the other

~~~json
{
  "protocol": "slipstream",
  "version": 1,
  "type": "file-error",
  "transferId": "b5c7f482-9d3e-4a20-a1ef-2d1c0f9f4b62",
  "code": "HASH_MISMATCH",
  "message": "The received file could not be verified."
}
~~~

Use these stable error codes:

| Code | Meaning |
|---|---|
| `INVALID_MESSAGE` | Malformed or invalid control message. |
| `UNSUPPORTED_VERSION` | Protocol version is not supported. |
| `INVALID_METADATA` | Offer metadata failed validation. |
| `TRANSFER_BUSY` | A different transfer is already active. |
| `TRANSFER_NOT_FOUND` | Message refers to no active matching transfer. |
| `UNEXPECTED_BINARY` | Binary data arrived outside the receiving state. |
| `INVALID_CHUNK_SIZE` | Chunk length does not match the expected length. |
| `SIZE_MISMATCH` | Final byte or chunk count does not match the offer. |
| `HASH_MISMATCH` | Computed SHA-256 differs from the offered digest. |
| `INTERNAL_ERROR` | Unexpected sender/receiver implementation failure. |

`message` is a short user-safe explanation. Do not expose stack traces, internal paths, or sensitive browser details. On a fatal transfer error, both sides stop the transfer, discard incomplete data, and enter a failed state. Avoid endless error-message loops: do not reply to a received `file-error` with another `file-error` unless there is a separate, clearly actionable local failure.

## 5. Transfer lifecycle and state transitions

### 5.1 Sender state machine

~~~text
IDLE
  -> HASHING
  -> OFFERING / AWAITING_ACCEPTANCE
      -> REJECTED (file-reject)
      -> CANCELLED (local cancel / file-cancel)
      -> FAILED (timeout, channel close, fatal error)
      -> SENDING (file-accept; send file-start)
          -> AWAITING_VERIFICATION (all chunks queued; send file-complete)
              -> COMPLETED (valid file-complete-ack)
              -> FAILED (file-error, timeout, channel close)
              -> CANCELLED (file-cancel)
~~~

The sender must not enter `SENDING` before a matching `file-accept` arrives. It must not enter `COMPLETED` merely because it has sent the last chunk.

### 5.2 Receiver state machine

~~~text
IDLE
  -> AWAITING_USER_DECISION (valid file-offer)
      -> REJECTED (user declines / validation rejects)
      -> CANCELLED (offer timeout or local cancellation)
      -> READY (user accepts; send file-accept)
          -> RECEIVING (matching file-start)
              -> VERIFYING (matching file-complete)
                  -> COMPLETED (digest and counts valid; send file-complete-ack)
                  -> FAILED (validation/hash error)
              -> CANCELLED (file-cancel / local cancel)
              -> FAILED (channel close / fatal error)
~~~

A new transfer cannot begin until the previous transfer has reached a terminal state and all temporary references have been cleared. Do not allow two active transfer IDs on the same channel. Handle duplicate messages idempotently where practical: do not create a second preview for a repeated matching offer, restart a completed transfer on a repeated start, or create a second download/ack for a repeated completion message.

### 5.3 Role and direction checks

| Message | Allowed sender | Receiver's action |
|---|---|---|
| `file-offer` | Host / sender | Validate metadata and show preview. |
| `file-accept` | Joiner / receiver | Begin sending. |
| `file-reject` | Joiner / receiver | Stop offer and return sender to ready state. |
| `file-start` | Host / sender | Initialise receiver's chunk counters. |
| Binary chunk | Host / sender | Validate length and append in order. |
| `file-progress` | Joiner / receiver | Update sender's progress display. |
| `file-complete` | Host / sender | Verify received size, chunk count and hash. |
| `file-complete-ack` | Joiner / receiver | Mark sender complete. |
| `file-cancel` | Either side | Stop and clean up the matching transfer. |
| `file-cancel-ack` | Side receiving cancellation | Confirm peer cleanup. |
| `file-error` | Either side | Fail and clean up the matching transfer. |

Reject or ignore a message that arrives from the wrong role or in an impossible state. Never let a joiner send file chunks in this release.

## 6. Back-pressure and progress

The sender must not queue an entire file into the data channel. Use `bufferedAmount` and `bufferedamountlow`:

| Setting | Phase 2 default |
|---|---:|
| Chunk size | 16 KiB |
| `bufferedAmountLowThreshold` | 256 KiB |
| Sender high-water mark | 1 MiB |

Implementation behaviour:

1. Before queuing another chunk, check that the channel is open and the transfer has not been cancelled.
2. When `bufferedAmount` is greater than the 1 MiB high-water mark, pause sending.
3. Resume when `bufferedamountlow` fires after the buffer falls to/below the 256 KiB low threshold. Re-check channel state and cancellation after waking.
4. Attach the low-buffer listener before waiting and re-check `bufferedAmount` after attaching it so the sender cannot miss an event between the check and listener registration.
5. Remove listeners and resolve/reject any pending wait when the transfer finishes, is cancelled, errors, or the channel closes.
6. Queue `file-complete` only after all chunks have been queued in order. It may follow queued bytes in the channel; the ordered channel preserves their sequence.

The receiver computes progress from validated bytes appended. Send throttled `file-progress` updates as described in Section 4.5. The receiver's UI can update on every chunk; the sender's UI updates when progress messages arrive. The connection trail and percentage must represent received bytes, not merely bytes read from the sender's File object or enqueued locally.

Do not display a fabricated speed or ETA. Derive speed from a rolling time/byte window and show it only after enough samples exist.

## 7. Module responsibilities and integration contract

Use the existing classic-script architecture. Do not introduce a framework, bundler, Node runtime, WebSocket server, or module system solely for Phase 2.

### 7.1 `js/webrtc.js` — Person 1 / integration owner

Keep `SlipstreamPeer` responsible for connection/signaling and generic data-channel transport only. It must not know about files, UI screens, hashes, or transfer states.

Add a consistent transport interface:

- `sendControl(message)`: validate the basic envelope and send `JSON.stringify(message)` as a string.
- `sendBinary(arrayBuffer)`: send one binary `ArrayBuffer` only when the channel is open.
- Keep the existing `send(data)` temporarily for Phase 1 test-chat compatibility; file modules must use `sendControl` and `sendBinary` instead.
- Add callbacks `onControlMessage(message)` and `onBinaryMessage(buffer)` to the constructor.
- Preserve the existing `onChannelMessage(data)` callback as a backward-compatible fallback during the transition, or update both host and joiner call sites together. Do not dispatch a message twice.

Incoming dispatch:

1. If `event.data` is a string, parse JSON.
2. If it is a Phase 2 envelope with `protocol: "slipstream"`, route it to `onControlMessage`.
3. If it is the legacy Phase 1 `{ type: "text", message }` message, route it to the existing Phase 1 chat handler, not to a file engine.
4. If it is an `ArrayBuffer`, route it to `onBinaryMessage`.
5. If it is a `Blob`, convert to `ArrayBuffer` in receive order, then route it to `onBinaryMessage`. If conversion is asynchronous, serialize conversions through a promise queue so adjacent chunks cannot be reordered.
6. Unknown or malformed data must never be appended as a file chunk or parsed as valid transfer control.

Keep `channel.binaryType = "arraybuffer"`. On channel close or peer error, notify `app.js` so it can stop the active sender/receiver, clear partial data, and show an interrupted state.

### 7.2 `js/file-sender.js` — Person 2

Expose a global `SlipstreamFileSender` class (the repository currently uses classic scripts).

Suggested public contract:

- Constructor: `{ peer, onStateChange, onProgress, onComplete, onError }`.
- `start(file)`: validate file, calculate SHA-256, create `transferId`, send `file-offer`, and wait for receiver response.
- `handleControlMessage(message)`: process matching `file-accept`, `file-reject`, `file-progress`, `file-complete-ack`, `file-cancel`, and `file-error`; ignore message types owned by the receiver.
- `cancel(reason = "user-cancelled")`: stop queuing chunks immediately, clean up locally, and send `file-cancel` when the channel is still open.
- `destroy()` or equivalent: remove pending listeners and release references.

The class owns sender-side chunking, back-pressure, send counters, timeout handling, and sender transfer state. It does not manipulate the DOM or navigate screens.

### 7.3 `js/file-receiver.js` — Person 3

Expose a global `SlipstreamFileReceiver` class.

Suggested public contract:

- Constructor: `{ peer, onOffer, onStateChange, onProgress, onComplete, onError }`.
- `handleControlMessage(message)`: process matching `file-offer`, `file-start`, `file-complete`, `file-cancel`, and `file-error`; ignore message types owned by the sender.
- `handleBinaryChunk(arrayBuffer)`: validate the expected chunk length and append it only while receiving.
- `accept()`: send `file-accept` for the current pending offer and prepare to receive.
- `reject(reason = "user-declined")`: send `file-reject` and clear the offer.
- `cancel(reason = "user-cancelled")`: discard partial data and send `file-cancel` when the channel is open.
- `destroy()` or equivalent: discard temporary data and release references/object URLs owned by the receiver.

The receiver owns metadata validation, chunk counting, reassembly, SHA-256 verification, and creation of a verified `Blob`. It must not create or expose a download link before successful verification. It does not manipulate the DOM.

The completion callback should provide the verified `Blob` and safe display metadata to the app; it should not create its own screen or click a download link.

### 7.4 `js/app.js` — Person 1 / integration owner

`app.js` remains the coordinator and single owner of application-level state and DOM events.

- Create one sender engine on the host and one receiver engine on the joiner after the peer data channel opens.
- Route `onControlMessage` to the sender and receiver handlers. Each module must safely ignore message types it does not own.
- Route `onBinaryMessage` only to the receiver engine. The host should never treat inbound binary data as a file transfer in this release.
- Connect the existing file picker/drag-drop and Send action to `sender.start(selectedFile)`.
- Connect the receiver's incoming-file preview Accept/Decline buttons to `receiver.accept()` / `receiver.reject()`.
- Connect Cancel to the active engine's `cancel()`; do not merely navigate away while a transfer continues.
- Update the existing transfer heading, subtext, trail fill, percentage, success checkmark, and screen states from engine callbacks.
- Create the receiver download URL only from the verified completion callback. Revoke the object URL during cleanup or after the download action has had time to start.
- On peer/channel close, call the active engine's local failure cleanup. Do not attempt to send a cancellation message through a closed channel.
- Keep Phase 1 test-chat handling separate from Phase 2 control messages.

Load scripts in this order in `index.html`:

1. `js/vendor/qrcode.min.js`
2. `js/api.js`
3. `js/webrtc.js`
4. `js/file-sender.js`
5. `js/file-receiver.js`
6. `js/app.js`

### 7.5 `index.html` and `css/style.css` — Person 4

Build the incoming-file preview and the transfer states around the protocol callbacks. The UI must show filename, type and size from the validated offer; Accept and Decline must be explicit; progress must be byte-derived; and success/download must wait for verification. Keep the existing Slipstream trail as the progress indicator—do not add a second competing progress bar.

The UI must distinguish at least: incoming offer, awaiting acceptance, transferring, verifying, completed, rejected, cancelled, connection interrupted, and integrity/protocol failure. Preserve mobile responsiveness and the existing visual tokens.

### 7.6 QA and graphics — Person 5

Use Section 10 as the minimum test contract. QA should report the transfer ID (or a shortened non-sensitive suffix), test file size, browser/device pair, expected result, actual result, and any console error. Do not include file contents or sensitive user data in test evidence.

## 8. Timeouts, disconnection, and cleanup

Use these initial defaults:

| Condition | Default behaviour |
|---|---|
| Receiver does not accept/reject an offer | Sender times out after 60 seconds; while the channel is open, it sends `file-cancel` with `reason: "timeout"`, then clears the pending offer and returns to ready state. |
| Data channel closes during offer/transfer/verification | Fail locally, stop work, discard incomplete data, and show interrupted. Do not claim the peer was notified. |
| User cancels while channel is open | Stop local work immediately, send `file-cancel`, and handle `file-cancel-ack` if received. |
| Sender does not receive `file-complete-ack` | After 60 seconds, mark the sender side interrupted/failed; do not claim sender-confirmed completion. The receiver may already have a locally verified file if it completed verification and sent the acknowledgement before the disconnect. |
| Channel closes while waiting for back-pressure | Reject the pending wait and terminate sender work. |
| Transfer is completed and acknowledged | Release temporary sender buffers and receiver chunk buffers; keep only the verified Blob/download state needed by the UI. |
| App resets or user disconnects | Cancel best-effort while open, destroy engines, close peer resources, revoke object URLs, and clear transfer references. |

Do not automatically retry a partially sent file in version 1. A retry is a new transfer with a new UUID and a fresh offer/accept handshake.

On any terminal failure, discard partial receiver chunks and do not create a download URL. If the receiver has already created a verified Blob, it may remain available for the current download action until the user leaves/resets the completed state; revoke its object URL during cleanup.

The original pairing session is for signaling. Once the data channel is open, file transfer uses the established peer connection and does not need additional PHP/MySQL requests. Deleting or expiring the signaling row must not be treated as a file-transfer progress event.

---

## 9. Validation and defensive handling

Both modules and the integration layer must validate messages, because data received from a peer is untrusted even though the channel is direct.

At minimum:

- Validate `protocol`, `version`, `type`, and UUID-shaped `transferId`.
- Validate role/direction and current state before acting on a control message.
- Accept only one active transfer ID.
- Validate filename length and render it with `textContent`; do not inject it into HTML.
- Validate `size`, `chunkSize`, `totalChunks`, MIME type length, timestamp, hash algorithm, and 64-character hexadecimal digest.
- Enforce the configured maximum file size before showing Accept as available.
- Check that every binary chunk has the exact expected byte length before appending it.
- Reject extra chunks, missing chunks, premature completion, wrong transfer IDs, unexpected binary data, and mismatched completion fields.
- Do not trust `mimeType` to determine whether a file is safe.
- Catch rejected promises from file reads, hashing, and data-channel operations. Convert them into a controlled failed state and clean up.
- Never use `innerHTML` with file metadata or peer-supplied error text.

A malformed or stale message must not cause a page crash, false success, or a download of incomplete data.

## 10. Required QA matrix

Run the following tests across two physical devices and at least two supported browser combinations where available.

| Test | Expected result |
|---|---|
| Empty file (0 bytes) | Offer/accept/start/complete/ack succeeds; verified empty download. |
| 1-byte file | One binary chunk; exact match after download. |
| 16,383-byte file | One chunk of 16,383 bytes. |
| 16,384-byte file | One full 16 KiB chunk. |
| 16,385-byte file | Two chunks; second chunk is 1 byte. |
| Multi-chunk file | Chunks arrive in order; byte count and SHA-256 match. |
| File at configured size limit | Accepted and transferred if resources permit. |
| File above configured size limit | Rejected before transfer with a clear explanation. |
| Unicode/long filename | Displayed as text without layout break or HTML injection. |
| Empty MIME type | Uses `application/octet-stream` and still transfers. |
| Receiver accepts | No binary bytes arrive before acceptance; transfer starts after accept. |
| Receiver declines | Sender stops waiting; no chunks are sent. |
| Receiver cancels during transfer | Sender stops; receiver discards partial data; no download appears. |
| Sender cancels during transfer | Receiver discards partial data; no download appears. |
| Channel drops mid-transfer | Both sides show interrupted/failed as appropriate; no false success or download. |
| Deliberate hash mismatch | Receiver sends `HASH_MISMATCH`; partial data is discarded. |
| Wrong transfer ID / unexpected binary | Message is ignored or rejected safely; active file is not corrupted. |
| Duplicate offer/control message | No duplicate transfer or duplicate download is created. |
| Back-pressure reached | Sender pauses and resumes; browser remains responsive; no unbounded buffering. |
| Phase 1 text test | Existing text exchange still works and is not treated as file control. |
| Receiver-side progress | Progress reflects validated bytes actually received. |
| Sender-side progress | Progress follows receiver `file-progress` messages and reaches completion only after ack. |
| Successful completion | Download appears only after size, chunk count, and SHA-256 all pass. |

Do not mark a test complete based only on two tabs in one browser. Final acceptance requires a real sender and receiver on separate physical devices.

## 11. Definition of Phase 2 done

Phase 2 is complete when:

1. A host can select one file and see its details before sending.
2. The sender calculates SHA-256 and sends a valid `file-offer` over the data channel.
3. The receiver sees the correct incoming-file details and can accept or decline.
4. The sender sends no file bytes before acceptance.
5. After acceptance, the sender transfers ordered 16 KiB binary chunks with back-pressure.
6. The receiver validates chunk lengths, reassembles the file, verifies total size/chunk count/SHA-256, and only then makes the file downloadable.
7. Both sides display progress derived from receiver-confirmed bytes.
8. The sender receives `file-complete-ack` before declaring success.
9. Rejection, cancellation, disconnect, malformed data, and hash mismatch all clean up correctly and never produce false success.
10. The Phase 1 connection and test-message path remain functional.
11. The full flow works between two physical devices on the intended local network.

## 12. Non-negotiable implementation decisions

For version 1, all agents must use the following same decisions:

- Host = sender; joiner = receiver.
- Existing `slipstream-transfer` data channel; ordered and reliable.
- Control messages = JSON strings using the common `slipstream` version 1 envelope.
- File data = raw `ArrayBuffer` messages, one ordered 16 KiB chunk per message.
- Only one active transfer per peer connection.
- Receiver acceptance is mandatory before any file bytes are sent.
- SHA-256 is calculated before the offer and verified after reassembly.
- The receiver sends throttled `file-progress` updates; both trails represent receiver-confirmed bytes.
- `file-complete-ack` is required before the sender marks success.
- No PHP/MySQL changes for file-transfer messages or bytes.
- No incomplete file is downloadable; cancellation, failure, or disconnect clears partial data.
- Preserve Phase 1 legacy text handling while implementing the new dispatch.

**If an agent believes one of these decisions must change, stop and coordinate with the integration owner first. Update this document and notify all agents before merging code that uses a different contract.**
